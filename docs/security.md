# Security notes

* The `rt_` API key is a **server-side secret**, never localized to the browser, used only in `wp_remote_*` calls. There is no API-key form field; supply it via the `PERSONA_ASSISTANT_API_KEY` wp-config constant (a legacy stored key is still honored), scoped to `CLIENT_TOKENS:WRITE` + `AGENTS:READ` + `PRODUCTS:SURFACES:READ`.
* The `ct_` client token **is** browser-safe (scoped to your origin and bound to your assistant's chat surface, rate-limited server-side).
* Provider API keys are never touched; built-in-AI calls stay server-side via `Persona_Assistant_AI`.
* The WP-AI REST endpoint always has a `permission_callback`. A "require login to chat" setting gates access, and a per-visitor, per-minute rate limit (default 10, filterable via `persona_assistant_wp_ai_rate_limit`, hard-capped 1-60) throttles usage; the `persona_assistant_rest_permission` filter remains available for stricter site-specific policy.
* The WordPress AI Client gates generation behind the `prompt_ai` capability (admins only by default). For a public widget, `Persona_Assistant_AI` grants `prompt_ai` only for the duration of the trusted server-side call, while the audience/rate-limit settings and `persona_assistant_rest_permission` filter remain the cost and abuse controls.
* Attachments are decoded and checked against the administrator's MIME/count/size policy before reaching a connector. WordPress AI Abilities are intersected with an explicit admin allowlist and must be marked read-only and non-destructive; their native permission callbacks still execute.
* WordPress AI requests include WordPress's REST nonce so cookie authentication, account-history ownership, and Ability permission callbacks see the actual visitor.
* Persona uses a plugin-supplied storage adapter. It persists only user/assistant text and strips attachments, inline file data, reasoning, tool activity, artifacts, and metadata before writing to session or device storage.
* Optional WordPress AI account history uses dedicated owner-scoped tables: `{prefix}persona_assistant_conversations` (public UUID, owning user ID, first-message title, timestamps, retention deadline) and `{prefix}persona_assistant_messages` (user/assistant **text only**, capped at the most recent 40 messages per conversation — the same stripping policy as the browser adapter applies before writing). It is disabled by default, full-screen Assistant Page only, retention-controlled (daily cron cleanup of expired rows, immediate deletion with the owning WordPress user), and registered with WordPress personal-data export and erasure. Every REST route and the chat endpoint's `conversationId` parameter revalidate ownership against the logged-in user. `uninstall.php` drops both tables permanently on plugin deletion; deactivation preserves them.
* Runtype remains canonical for Runtype transcripts; WordPress stores no duplicate transcript and remembers only an opaque session ID for the selected browser lifetime.
